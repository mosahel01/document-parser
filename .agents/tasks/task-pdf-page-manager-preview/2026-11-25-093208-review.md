# PDF page manager — rotate thumbnails, range selection, lightbox, and auto-preview (v1)

The commit adds four features to `PdfPageManager.tsx`: thumbnails now rotate visually when a slot's `turn` changes, the toolbar gains a range-selection input, any page card can be double-clicked to open a full-size lightbox, and after certain in-place edits the PDF preview is rebuilt automatically when the document has 20 or fewer pages. The approach is entirely client-side and self-contained in one file. All 174 tests pass.

**Watch for:**
- Lightbox rotate actions set `autoPreviewPending` only implicitly through `book.slots` changes (the effect fires for every slot mutation), but the per-card toolbar rotate and the lightbox rotate follow different code paths — the per-card one sets the flag explicitly, the lightbox one does not (confirmed).
- When a range parse returns an error or zero matches, the selection is left at whatever it was before rather than cleared (confirmed).
- The lightbox image applies `rotate(Ndeg)` but `max-h-[70vh]` is measured in the unrotated frame, so a 90° or 270° page renders visually taller than 70 vh until the browser clips it (confirmed).

**Verdict**: NEEDS_CHANGES

---

## High-level view

The range input wires directly to `parsePageSelection`, the same parser the split/extract tools already use. Typing replaces the selection; the existing "Clear" button now also resets the range field. The range input is one-way: it only sets the selection, it never reads it back, so using the mouse to click individual cards while there is text in the range box leaves the box stale. When the parse fails (bad token, out-of-range page), the error is silently discarded.

The lightbox renders the same thumbnail blob the grid uses. The rotate and delete actions in the lightbox modify `book.slots` through `setBook` directly, not through `turnSelected` or `deleteSelected`. That means they bypass the `autoPreviewPending.current = true` flag, so a lightbox rotation on a ≤20-page document does not auto-preview (confirmed).

Auto-preview is gated at 20 pages, using a `useRef` flag read by a `useEffect` that watches `book.slots`. The flag is set by `turnSelected`, `duplicateSelected`, `deleteSelected`, and the per-card rotate button, but not by the lightbox rotate buttons. The 20-page threshold keeps the trigger out of large documents where a rebuild would be slow.

<details>
<summary>Issues (4)</summary>

1. **Lightbox rotate skips auto-preview** — `setBook` in the lightbox's rotate buttons does not set `autoPreviewPending.current = true`, so a rotation performed in the lightbox on a ≤20-page document does not update the preview. Add `if (book.slots.length <= 20) autoPreviewPending.current = true` after each `setBook` call in the two lightbox rotate handlers.

2. **Stale range input after manual selection change** — The range input is write-only: it sets the selection but does not synchronise when the user clicks cards manually. After typing "1-3", clicking card 4 adds it without clearing the range field, leaving "1-3" displayed while the actual selection is "1-3, 4". Either make the field read-write (clear it when the selection diverges) or note in the placeholder that it replaces the selection.

3. **Lightbox image overflows 70 vh at 90°/270° rotations** — `max-h-[70vh]` applies to the element's layout box before the CSS `rotate()` transform. At 90° or 270°, the visually tall axis is the element's layout width, not its height, so the constrained dimension is wrong. The image renders taller than the viewport until the browser clips it at the modal boundary. Use `max-w-[70vh] max-h-[70vw]` when rotation is 90 or 270, or wrap the image in a container sized to the rotated bounds.

4. **Range parse error gives no visible feedback** — `handleRangeChange` silently does nothing when `result.error !== null`: the selection stays unchanged and no message is shown. A user typing "1-50" into a 10-page document sees no response until they notice nothing happened. Surface the error inline (e.g. a small red label below the input) to match the behaviour of the range input in the split tool.

</details>

<summary>Details</summary>

### Lightbox rotate bypasses auto-preview

The two rotate buttons inside the lightbox call `setBook` directly:

```tsx
setBook((current) => ({
  ...current,
  slots: current.slots.map((s) =>
    s.id === lightboxId ? { ...s, turn: (s.turn + 90) % 360 } : s,
  ),
}))
```

There is no `autoPreviewPending.current = true` here. The per-card toolbar rotate (`↻` button in the grid row) does set the flag, as does `turnSelected`. The lightbox rotate does not, so a rotation performed in the lightbox on a ≤20-page document will not trigger a preview rebuild even though the visual thumbnail updates immediately.

### Range input synchronisation gap

`handleRangeChange` selects pages when the parse succeeds, but does nothing when it fails:

```ts
function handleRangeChange(value: string) {
  setRangeInput(value)
  if (value.trim() === '') return
  const result = parsePageSelection(value, book.slots.length)
  if (result.error === null && result.pages.length > 0) {
    const ids = new Set(result.pages.map((idx) => book.slots[idx].id))
    setSelected(ids)
  }
}
```

When `result.error !== null` (page out of range, bad token, reversed range), the error goes nowhere — no message, no visual indicator, no selection change. `parsePageSelection` returns a typed `error` string in those cases, identical to what the split tool shows inline. Surfacing it here would be a one-line addition.

The input is also one-directional: manual card clicks update `selected` but not `rangeInput`. After clicking a card while the range field reads "1-3", the field continues to display "1-3". Clearing the field via the × button does reset selection, so the escape hatch exists, but the stale state is a confusing default.

### Lightbox image overflow at non-zero rotations

The lightbox image uses:

```tsx
<img
  style={{ transform: `rotate(${lbSlot.turn}deg)` }}
  className="max-h-[70vh] object-contain mx-auto"
/>
```

CSS `transform` does not affect layout: `max-h-[70vh]` constrains the element's pre-rotation height. At 90° the element is laid out horizontally (its layout height is the original width), so `max-h-[70vh]` applies to the wrong dimension. The rotated image can extend beyond the viewport's visible area until the `max-h-[90vh]` on the modal container clips it. The fix is to either size the wrapper to match the rotated bounds or apply `max-w-[70vh]` for 90°/270° pages.

### Test coverage

No new tests were added. The auto-preview flag/effect pair has a directly testable edge — a lightbox rotation should set `autoPreviewPending` to `true` on a ≤20-page document — but it is currently untested, and the lightbox rotate bug would be caught by exactly that test.
